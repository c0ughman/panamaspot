# SEO Audit & Implementation Plan — PanamaSpot article pages

**Audit date:** 2026-07-20
**Scope:** 48 article HTML pages under `public/articles/` (EN) and `public/es/articles/` (ES), plus `src/app/sitemap.ts` / `src/app/robots.ts`.
**Status:** Findings only. Nothing here is implemented yet. Hand to implementation agent.

## How this site is built (important context for the implementer)
- Article pages are **static HTML** in `public/articles/*.html` and `public/es/articles/*.html`. These are the live source of truth (e.g. `panamaspot.com/articles/volcan-baru-hike-sunrise-summit-guide`). **Edit the HTML directly.**
- `sitemap.xml` and `robots.txt` are **generated by Next.js** from `src/app/sitemap.ts` and `src/app/robots.ts` (both `force-static`). Edit the `.ts` files, not the generated output in `out/`/`.next/`.
- Images on the guide pages are CSS `background-image` on `<div class="imgph photo">`, **not `<img>` tags**. The hero lives in `.art-hero-img-full` plus `og:image`/`twitter:image`/JSON-LD (kept in sync by `scripts/image-swap.py`).
- Per-page "Image credits" block is generated by `scripts/image-credits.py`; image selections live in `scripts/image-selections.json`.

## What is already GOOD (do not touch)
- `<title>` on every page (mostly 48–66 chars). Unique per page.
- `<meta name="description">` on every page (135–177 chars). Unique.
- `<link rel="canonical">` on every page.
- **hreflang** `en` / `es` / `x-default` alternates on every page (in-page).
- Open Graph (7 tags) + Twitter Card (`summary_large_image`, 5 tags) on every page.
- JSON-LD is rich and valid: `Organization`, `WebSite`, `BreadcrumbList`, `Article` (headline, description, image, datePublished, dateModified, inLanguage, isAccessibleForFree, articleSection, author, publisher, mainEntityOfPage, url), and `FAQPage`.
- Exactly one `<h1>` per page. `lang` attribute correct (en/es).
- `robots.ts` allows all + points to sitemap. `robots` meta = `index, follow`.

### C2 — Images are CSS backgrounds → zero image-search visibility + no alt text (accessibility)
~34 of 48 pages render hero/gallery/bento as `background-image` on `<div class="imgph photo">`. Consequences: **no Google Images traffic**, screen readers announce nothing, and only the hero is in structured data. (The hikes/tours/things-to-do/senderos cluster already uses real `<img>` with alt — inconsistent.)

**Fix — pick one lane:**
- **Best (higher effort):** convert hero + gallery + bento `imgph` divs to real `<img loading="lazy" width= height= alt="…descriptive, localized…">` with a CSS object-fit cover, keeping the current look. Requires updating `scripts/image-swap.py` / `image-credits.py` output templates so it stays regenerable, and writing alt text (reuse the captions we already authored in `image-selections.json`).
- **Lighter (lower risk, partial win):** keep backgrounds but (a) add `role="img"` + `aria-label="<caption>"` to each `imgph` div for accessibility, and (b) enrich the `Article` JSON-LD `image` array to list **all** page images (currently only the hero) as `ImageObject{contentUrl, caption}`. This recovers structured-data/image signals and a11y without a layout change, but still no true `<img>` for Google Images.

**Recommendation:** do the lighter lane now (fast, safe), schedule the full `<img>` conversion as a follow-up. Alt text source = the ES/EN captions already in `image-selections.json`.
**Effort:** medium (light) / high (full). **Risk:** medium.

### C3 — Full-resolution originals served as backgrounds → poor LCP / Core Web Vitals
119 distinct Wikimedia images are referenced by their **original** `upload.wikimedia.org/.../Name.jpg` URLs (many 4000–14000 px wide; e.g. `Coibita_Island_Panorama.jpg` is 11722 px). Each is downloaded full-res as a background image. The **hero is the LCP element** on mobile — a multi-MB image there directly hurts the Core Web Vitals ranking signal.

**Fix:** width-cap every Wikimedia image URL. Hero → ~1600px, gallery/bento/inline → ~1000px, using either `https://commons.wikimedia.org/wiki/Special:FilePath/<file>?width=1600` (redirects to an allowed thumb) or a direct CDN thumb `/thumb/…/1600px-<file>` (allowed widths incl. 1280/1920). Bake the width-cap into `scripts/image-swap.py` (`esc_bg`) and `image-credits.py` so it's regenerable. **Note:** the credits collector matches `upload.wikimedia.org` and derives the Commons filename — keep that working (Special:FilePath uses `commons.wikimedia.org`, so if you switch schemes, update the collector regex, or prefer the `/thumb/…/1600px-` form which stays on `upload.wikimedia.org`).
**Effort:** medium. **Risk:** medium (touch the generators + re-run + re-verify all pages). **Payoff:** large (LCP).

## 🟡 MODERATE

### M1 — Stale `dateModified` / `article:modified_time` / sitemap `lastmod`
All 24 overhauled pages still show `dateModified` = `2026-07-16` (and older on others); none reflect the 2026-07-19/20 image refresh. Freshness is a ranking signal and we materially changed these pages.
**Fix:** bump `article:modified_time` (meta) **and** `Article.dateModified` (JSON-LD) **and** the sitemap `lastModified` to the real edit date for every page we changed. Keep `datePublished` untouched. Automate in `scripts/image-swap.py` (stamp `dateModified` on write) so it never drifts again.
**Effort:** low–medium. **Risk:** low.

### M2 — `og:image:alt` and `twitter:image:alt` missing on all 48 pages
No alt for the social-share image → weaker accessibility + preview quality.
**Fix:** add `<meta property="og:image:alt" content="…">` and `<meta name="twitter:image:alt" content="…">` using the hero caption. Automate in `image-swap.py`'s `set_hero`.
**Effort:** low. **Risk:** low.

### M3 — `og:image:width` / `og:image:height` missing on all 48 pages
Recommended so platforms render the card without fetching the image first.
**Fix:** add `og:image:width`/`og:image:height` (use the capped hero dimensions from C3, e.g. 1600×N). Automate in `set_hero`.
**Effort:** low. **Risk:** low.
